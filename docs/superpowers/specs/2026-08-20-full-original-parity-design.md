# Full Original Parity Design

## Purpose

This document defines the Phase 2 architecture for bringing `mcpi-recompiled` from the Phase-1 functional compatibility foundation to evidence-backed original-behavior parity with Minecraft: Pi Edition 0.1.1 alpha.

The project remains an independent source reconstruction. The original executable and Mojang/Microsoft-owned assets are reference inputs only and are never committed. No leaked source, copied decompiler output, modified original binary, or redistributed proprietary game data may enter the repository.

`v0.1.0` remains the stable Phase-1 fork point. Phase 2 is developed on `phase2/full-original-parity` in one large pull request, but the implementation is split into reviewable commits and subsystem gates.

## Success model

Parity is evidence-driven, not assertion-driven. Each tracked item has one of four statuses:

- `confirmed` — the original behavior/layout/protocol detail has direct evidence but no full implementation match yet;
- `matched` — reconstructed behavior is covered by an automated or documented original-vs-recompiled comparison;
- `partial` — meaningful compatible behavior exists, but one or more known original behaviors are not yet matched;
- `unknown` — insufficient original evidence exists to make a claim.

A checklist item is marked complete only when all required subclaims for that item are `matched` or the remaining original behavior is demonstrated to be unreachable/dormant in the Pi 0.1.1 target.

## Global constraints

1. C++20 remains the language baseline.
2. Linux x86-64 and Windows x86-64 must stay green throughout Phase 2.
3. Java compatibility continues to compile and smoke-test under Java 25.
4. The MCPI API remains available on TCP port 4711 by default.
5. The original world remains finite at 256×128×256 unless evidence proves a different reachable Pi behavior.
6. Original assets are optional user-provided inputs. The repository ships legal fallbacks only.
7. CI may contain compact reference vectors, hashes, expected protocol transcripts, independently derived constants, and screenshots generated by the reconstruction; it may not contain the original executable or proprietary asset pack.
8. Every behavior change follows RED → GREEN testing where practical.
9. Reverse-engineering notes must distinguish confirmed observations from inference.
10. Phase 2 does not modernize gameplay. Modernization belongs in a separate fork.

## Architecture

### 1. Parity oracle and reference-vector layer

Add a repository-owned parity framework under `tests/parity/` and `src/parity/`.

A `ReferenceCase` identifies a subsystem, case name, source-build identifier, input payload, and expected result. Expected results are small derived artifacts such as block IDs, heights, metadata/light nibble arrays, protocol replies, movement traces, save metadata, hashes, and camera transforms.

The framework never launches or bundles the original binary in CI. Instead, reference cases are captured locally from a legally obtained original MCPI installation using separate tooling and committed only after review that the data is factual/derived and not a proprietary file dump.

Core interfaces:

```cpp
namespace mcpi::parity {

enum class Status { Unknown, Confirmed, Partial, Matched };

struct ReferenceCase {
    std::string subsystem;
    std::string name;
    std::string reference_build;
    std::string input;
    std::string expected;
};

struct Comparison {
    bool matched;
    std::string actual;
    std::string expected;
    std::string detail;
};

Comparison compare_text(const ReferenceCase& reference, std::string actual);
std::string stable_hex_digest(std::span<const std::uint8_t> bytes);

}
```

`docs/parity-status.md` becomes the canonical 20-item status matrix and links each claim to a test or RE note.

### 2. World/chunk fidelity

The current `WorldGenerator` Phase-1 interpolated height function is replaced by an explicit source chain mirroring the observed original responsibilities:

```text
Level
  -> ChunkSource
      -> RandomLevelSource
          -> LevelChunk
```

New world-generation code must produce a complete 16×128×16 chunk state: block IDs, metadata, skylight, block light, and height map. Generation is deterministic for a seed and chunk coordinate. The finite 16×16 chunk grid is generated lazily or eagerly without changing observable results.

The known LevelChunk storage facts remain authoritative unless stronger evidence supersedes them:

- block index `(x << 11) | (z << 7) | y`;
- 32768 block ID bytes;
- 16384-byte packed nibble arrays for data, sky light, and block light;
- 256-byte height map;
- Y range 0..127 internally.

World generation is not declared matched until selected reference seeds match original chunk fingerprints and sampled coordinates.

### 3. Lighting and block updates

Lighting becomes a first-class world subsystem rather than passive stored nibble arrays.

Interfaces:

```cpp
class LightEngine {
public:
    void rebuild(World& world);
    void on_block_changed(World& world, const BlockPos& pos,
                          BlockState before, BlockState after);
};

class BlockBehaviorRegistry {
public:
    const BlockBehavior& behavior(int block_id) const;
    void neighbor_changed(GameState& game, const BlockPos& pos,
                          const BlockPos& changed_neighbor) const;
    void scheduled_tick(GameState& game, const BlockPos& pos) const;
};
```

Block definitions carry opacity, light emission, metadata semantics, placement rules, replaceability, tick behavior, and collision shape. Only behaviors reachable in original Pi 0.1.1 are required for completion.

### 4. Original save/storage compatibility

Introduce a storage abstraction and keep the Phase-1 `.mcpiworld` format only as a migration/debug format.

```cpp
class LevelStorage {
public:
    virtual ~LevelStorage() = default;
    virtual bool load(GameState& game, const std::filesystem::path& path) = 0;
    virtual bool save(const GameState& game, const std::filesystem::path& path) = 0;
};
```

`PiLevelStorage` reconstructs original metadata/chunk persistence from observed `LevelStorage` / `ExternalFileLevelStorage` / LevelData/NBT behavior. Storage code must preserve seed, spawn, player state, settings, chunk IDs/data/light/height fields, and any other verified reachable state.

World-save parity is complete only when a reconstructed save can round-trip through the reconstruction and, where the original format is confirmed, exchange test worlds with the original reference installation without corrupting the tested fields.

### 5. Simulation core and tick loop

Replace direct Phase-1 movement with a deterministic fixed-step simulation.

Core objects:

```cpp
struct Aabb {
    Vec3 min;
    Vec3 max;
};

struct Velocity {
    double x;
    double y;
    double z;
};

class Entity {
public:
    virtual ~Entity() = default;
    int id() const noexcept;
    Vec3 position() const noexcept;
    Velocity velocity() const noexcept;
    const Aabb& bounds() const noexcept;
    virtual void tick(GameState& game);
};

class Player final : public Entity {
public:
    Inventory& inventory() noexcept;
    const Inventory& inventory() const noexcept;
    bool on_ground() const noexcept;
};

class GameLoop {
public:
    static constexpr double tick_seconds = 1.0 / 20.0;
    void tick(GameState& game);
};
```

The exact original tick rate/order remains evidence-driven. `1/20` is a provisional default only until timing evidence confirms or replaces it; parity status must show that distinction.

Physics covers collision resolution, gravity, jumping, ground state, wall/ceiling constraints, movement speed, reach/eye position, water movement if reachable, and flight only where original Pi supports it/settings enable it.

### 6. Inventory/items

Replace `std::array<int, 9>` hotbar storage with item stacks and an inventory model.

```cpp
struct ItemStack {
    int item_id = 0;
    int count = 0;
    int data = 0;
};

class Inventory {
public:
    static constexpr int hotbar_size = 9;
    ItemStack& slot(int index);
    const ItemStack& slot(int index) const;
    int selected_slot() const noexcept;
    void select(int index) noexcept;
};
```

Creative selection, stack sizes, item data, persistence, and UI presentation are reconstructed only from reachable original behavior.

### 7. Entity model

API entity operations no longer alias every entity ID to local player 0. Add an entity registry with stable runtime IDs and explicit local player identity. Only entity classes confirmed reachable in Pi are implemented as parity targets; dormant MCPE ancestry is documented but not treated as required gameplay.

Block-hit events are emitted by actual player interaction and consumed by MCPI API polling.

### 8. Networking/multiplayer

Create `src/network/` with packet framing, packet types, client/server handlers, and session state based on observed Pi networking symbols and reachable behavior.

The implementation must first determine whether local multiplayer paths in the Pi binary are reachable and to what extent. If a network class exists only as inherited/dormant MCPE code and cannot be reached in Pi 0.1.1, documentation proving that is sufficient for that subclaim. No invented multiplayer UI or protocol is added merely because symbols exist.

### 9. MCPI API bug-for-bug compatibility

Split protocol parsing/formatting semantics from command behavior. Add transcript-driven tests for:

- argument count handling;
- malformed integers/floats;
- `Fail` versus no response;
- rounding/flooring and negative coordinates;
- spawn-relative translation;
- finite-world clamps;
- `setBlocks` normalization;
- chat punctuation/commas;
- camera commands;
- event polling/clearing;
- entity/player-id behavior;
- unknown commands.

Reference transcripts take precedence over assumptions in the current dispatcher.

### 10. Java and Python API compatibility

The bundled/known Pi API surface becomes the contract.

Java package `pi` must include all classes, nested helpers, method signatures, constants, camera/events/entity wrappers, `Block`, vectors, and connection behavior required by the original examples. The build produces a reusable JAR in addition to smoke-testing classes.

Python compatibility is verified using the modern `mcpi` package and a repository-owned compatibility test suite modeled on the original Pi examples. Where Python-2-era formatting or behavior differs, tests document the original result and the supported modern equivalent.

### 11. Renderer and camera

Replace the Phase-1 height-surface painter with a real voxel/chunk renderer. Rendering responsibilities are separated:

```text
ChunkMeshBuilder -> opaque/translucent geometry
LevelRenderer    -> visible chunks, selection, particles
EntityRenderer   -> entities/player when visible
Camera           -> normal/third/fixed modes
HudRenderer      -> hotbar/chat/crosshair/screens
```

Required capabilities include face culling, depth testing, per-face texture coordinates, transparency ordering suitable for the original blocks, sky/fog, lighting modulation, selection outline, original-style FOV/camera transforms, and renderer use of LightEngine data.

SDL3 remains the platform/window/input abstraction unless evidence requires a behavior-specific compatibility layer.

### 12. Asset loading

Add a user-supplied asset locator. It may scan an explicit `--assets <path>` argument and known local installation directories, but must not download proprietary assets.

```cpp
class AssetSource {
public:
    virtual ~AssetSource() = default;
    virtual std::optional<std::vector<std::uint8_t>> read(std::string_view path) const = 0;
};
```

`OriginalPiAssetSource` validates expected filenames/dimensions/hashes where known. `FallbackAssetSource` supplies project-owned minimal textures/font/silent audio so the binary remains runnable without original assets.

### 13. Audio

Add SDL3 audio output and a `SoundEngine` that resolves sound events through the asset source. Missing original sounds are non-fatal and use silence/fallback behavior. Positional attenuation and event timing are matched only where evidence exists.

### 14. Original UI

Implement original-reachable screens and HUD states: title/main flow, in-game HUD, pause flow, hotbar/item rendering, crosshair, chat, buttons, and world selection/creation elements that are actually present in Pi 0.1.1. Layout uses the original 848×480 reference coordinate system and scales predictably for modern windows.

### 15. Camera API integration

`camera.mode` and `camera.setPos` state becomes authoritative input to the renderer. Normal, third-person, fixed-position, and follow behavior are matched using reference traces/screenshots. Camera/entity target state is represented explicitly rather than hidden in the dispatcher.

### 16. Original game loop and input order

Reconstruct tick/update/render ordering around the known application startup and `Minecraft`/`NinecraftApp` call graph. Input sampling, world tick, player tick, entity tick, API changes, chunk rebuilds, audio events, and render submission are ordered according to evidence. Pause semantics and timing are included.

### 17. Reverse-engineering class map

Expand `docs/reverse-engineering/` with one concise document per major subsystem and a machine-readable anchor index.

Required target names include at least:

- `Minecraft` / `NinecraftApp`;
- `Level`, LevelData, storage classes;
- `ChunkSource`, `ChunkCache`, `RandomLevelSource`, `LevelChunk`;
- player/entity/inventory classes;
- renderer classes;
- network handlers/packets;
- UI/screen classes;
- camera/position translator classes.

Each mapped function records address/range when known, evidence type, confidence, and independently written summary.

### 18. Differential harness

The parity test runner supports subsystem filters and emits human-readable mismatches plus machine-readable JSON. Reference data is versioned by source-build fingerprint. CI runs only committed safe vectors; local researchers may run capture utilities against a user-provided original installation.

Core command shape:

```text
mcpi-parity --suite worldgen --references tests/parity/reference
mcpi-parity --suite api --references tests/parity/reference
```

### 19. Platform expansion

Linux x86-64 and Windows x86-64 stay release blockers. Add build-only/smoke targets where hosted runners permit:

- Linux ARM64 cross/native;
- Raspberry Pi ARM64 runtime recipe;
- historical ARM32 build recipe where toolchain support is practical;
- macOS x86-64 and Apple Silicon.

A platform is marked complete only when configure/build/tests are reproducible and documented. Historical ARM32 may remain `partial` if current GitHub-hosted infrastructure cannot execute it, but a reproducible toolchain/build must still be supplied before that item can be closed.

## The 20-item acceptance matrix

1. Original world generation — reference-seed chunk/height fingerprints match.
2. Lighting — sky/block propagation and update cases match.
3. Original block behavior — verified metadata, placement, neighbor, tick, liquid/dynamic cases match reachable original behavior.
4. Original world save format — tested metadata/chunk round-trip and original interchange for confirmed fields.
5. Player physics — movement/collision/jump/gravity traces match.
6. Inventory/hotbar/items — slot/item/selection/persistence behavior matches.
7. Entity system — runtime IDs, player/entity movement/ticks/events match reachable entities.
8. Networking/multiplayer — reachable Pi behavior matches or dormant code is demonstrated and documented.
9. Minecraft renderer — reference scenes match geometry/camera/visibility/lighting semantics; exact proprietary pixels are not required without user assets.
10. Original asset loader — user-provided original assets load without repository redistribution and legal fallback remains runnable.
11. Audio — reachable sound events, lookup, playback timing/attenuation match where evidence exists.
12. Original UI — reachable 848×480 layouts/state transitions match reference behavior.
13. Camera — API camera modes/position/target visibly affect rendering and match traces.
14. MCPI API bug-for-bug — committed command transcripts pass.
15. Java API complete — original examples/signatures compile and integration tests pass; JAR produced.
16. Python API complete — original-style examples and modern `mcpi` compatibility suite pass.
17. Original game loop — tick/update/render/pause ordering tests match observed traces.
18. More class map — required major subsystem anchors documented with confidence/evidence.
19. Differential harness — safe committed vectors, local capture flow, CLI filtering, JSON report, CI integration all work.
20. Platforms — Linux/Windows release targets plus documented/tested ARM/macOS targets meet the platform completion rules above.

## PR and commit policy

All Phase-2 implementation is kept in the single pull request from `phase2/full-original-parity` to `main`, as requested. Inside that PR:

- every subsystem starts with a failing test/contract where practical;
- commits remain scoped (`parity`, `worldgen`, `lighting`, `storage`, `simulation`, `api`, `renderer`, etc.);
- `docs/parity-status.md` is updated only when evidence changes status;
- no large generated binary artifacts are committed;
- no item is marked complete merely because a class or placeholder exists.

## Initial execution order inside the monster PR

1. parity status schema + reference-vector harness;
2. RE anchor index and worldgen capture format;
3. RandomLevelSource reconstruction;
4. light engine + block behavior registry;
5. original storage/NBT/chunk persistence;
6. simulation clock, collision, player, inventory, entities;
7. reachable networking;
8. MCPI transcript parity + Java/Python completeness;
9. chunk renderer/camera/assets/audio/UI;
10. platform matrix and final cross-subsystem acceptance report.

This ordering does not create separate PRs; it prevents later systems from being built on known Phase-1 placeholders.
